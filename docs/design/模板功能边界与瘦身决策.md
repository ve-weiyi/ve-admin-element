# 模板功能边界与瘦身决策

> 适用范围：blog-admin（Vue 3 + Element Plus + Vite 后台前端）
> 决策日期：2026-09-11
> 关联分支：`feature/main`（基于 `release/template`）

## 一、背景

blog-admin 于 2026-05-30 基于 vue3-element-template 的模板快照改造而来。此后模板侧与业务侧各自演进，形成结构性分叉：

- **模板侧**于 2026-09-11 同步至上游 2026-08-06 版本，带来基座重构（依赖与构建链、类型体系、布局体系、主题体系、样式组织、请求层等）
- **业务侧**（main 分支）在模板之上实现了博客管理后台，并对部分模板基础设施做了业务适配

两边的最佳公共祖先是 2026-05-30 的模板快照。

## 二、目标与约束

**目标**：以新模板为基座重建 blog-admin，并借此机会对模板做一次**功能层面的瘦身**——删除与博客后台无关的内容，保留后台框架的基础能力。

**约束**：

1. 迁移期间项目必须可构建、可运行（类型检查、构建、开发态启动均需通过）
2. 业务资产（博客后台的功能实现）零丢失
3. 不引入模板之外的特异化改造，保持后续可持续跟进上游模板的能力

## 三、判断原则

一个模板内容该不该保留，判断标准是：**它是否服务于后台框架的基础能力，而非模板作者自用的演示内容或开发工具。**

- **保留**：任何后台都需要的能力——布局、认证、权限、通用组件、通知、个人中心等
- **删除**：模板作者自用的开发工具、宣传演示资源、与后台无关的示例

**不以"某个分支删过什么"作为判断依据。** 上游或派生分支的删除动作往往伴随后续的重写，删除不等于不需要。典型例证见第五节。

## 四、功能边界决策

### 4.1 保留：后台框架基础能力

| 功能域 | 内容 | 保留理由 |
|---|---|---|
| 页面布局 | 四种布局模式（左 / 上 / 混合 / 双列）、侧边栏、导航栏、标签页、工具栏、布局设置面板、面包屑 | 后台框架骨架 |
| 认证 | 登录、注册、重置密码 | 接入任何业务前必需 |
| 首页 | 仪表盘 | 登录后默认落地页 |
| 消息通知 | 顶栏通知下拉、通知列表页 | 后台通用能力 |
| 个人中心 | 用户资料页 | 后台通用能力 |
| 错误页 | 401 / 404（共用外壳） | 路由兜底 |
| 外链与跳转 | iframe 外链页、路由重定向页 | 菜单外链能力的依赖 |
| 通用组件 | CURD 三件套、分页、字典选择与字典标签、上传、富文本、图标选择、命令面板、全屏、语言切换等 | 业务页面复用的基础 |
| 状态与路由 | 应用 / 权限 / 设置 / 标签页 / 用户 / 字典等状态，路由守卫与动态路由 | 框架运行必需 |
| 请求与工具 | 请求封装、鉴权存储、主题、下载、格式化、校验等 | 框架运行必需 |
| **系统管理** | 用户、角色、菜单、部门、字典、参数、日志、通知 | **后台 RBAC 基础能力，属框架而非博客业务** |
| 实时通信 | SSE 通道（字典同步、在线人数、系统消息、通知、心跳） | 当前已接线，见 4.3 |

**关于系统管理的取舍**：该模块在派生分支中曾被删除，但随后又以重写形式回归。它的功能（账号、角色、菜单、权限、字典、参数、日志、公告）是任何后台的通用能力，与博客业务无关，因此保留。其实现会在业务搬迁阶段被重写版替换。

### 4.2 删除：与博客后台无关

| 内容 | 删除理由 |
|---|---|
| 代码生成器（页面、API、相关枚举） | 面向开发者的脚手架工具，运行时后台不需要 |
| vxe-table 及其配置与样式 | 模板中已无任何使用者，属历史残留 |
| 代码编辑器依赖 | 唯一消费者是代码生成器的预览步骤；生成器删除后成为死依赖 |
| 模板演示图片（应用 / PC 预览图、作者二维码） | 模板作者的宣传素材 |
| 模板英文版 README | 模板作者的文档，非本项目文档 |
| 指向已删页面的 mock 菜单项 | 菜单数据与实际页面不一致 |

### 4.3 明确不在本次处理范围

**实时通信机制替换（SSE → STOMP）**：这是机制变更而非内容删除，与基础设施适配同期进行，避免中间态断裂。本次瘦身保留 SSE 现状。

## 五、与派生分支改造的关系

派生分支相对模板快照的改动分两类，迁移中处理方式不同：

| 类别 | 内容 | 迁移方式 |
|---|---|---|
| 业务资产 | 博客后台各功能模块及其 API、路由、组件、状态、枚举 | **整体搬迁** |
| 基础设施适配 | 请求层、鉴权、错误码契约、上传、权限处理等对模板的改造 | **逐项复核后重新落地** |

基础设施适配不能照搬：模板已重构同名机制，旧适配中可能存在已无必要的部分，需要按新模板的实现重新判断。

**一个典型例证**：派生分支早期的"减支"提交删除了模板的系统管理页面，两天后的"博客"提交又以自己的实现重写并回归了同等功能。这说明**删除动作反映的是"即将重写"，而非"不需要"**，故本次瘦身不以其删除清单为依据。

## 六、迁移分期（决策层）

| 阶段 | 内容 | 边界特征 |
|---|---|---|
| 1. 模板瘦身 | 落地本决策 | 项目保持可运行 |
| 2. 工程化基座 | 依赖、构建链、类型体系骨架 | 与业务解耦 |
| 3. 类型体系与 API 层 | 决定全局类型的组织方式 | 影响面广，需先定型 |
| 4. 基础设施适配 | 请求、鉴权、路由、公共组件、上传 | **唯一的硬骨头** |
| 5. 业务模块搬迁 | 博客后台各功能模块 | 纯追加，风险最低 |
| 6. 验证与收口 | 全链路验证、monorepo submodule 指针同步 | — |

分期遵循的原则：**先拆除、后替换、再追加**。删除与替换分开，避免同一步内既拆旧又立新导致难以定位回归。

## 八、权衡

**为什么以新模板为基座，而不是把模板更新合进旧代码**：旧代码对模板基础设施的侵入较深，若以旧代码为基座，每次模板升级都要重复处理同一批侵入点。以新模板为基座可一次性把基座对齐上游，后续升级成本显著降低。代价是基础设施适配需要重做一遍。

**为什么瘦身先于业务搬迁**：瘦身是"拆除"，业务搬迁是"追加"。先拆除可以让后续替换基础设施时不必再维护即将废弃的页面；若顺序颠倒，替换期间需要同时兼容两套页面的调用方式。

**为什么保留系统管理而不随派生分支删除**：判断依据是功能是否属于后台通用能力，而非某分支的历史动作。保留可让瘦身后仍是一个可用的后台骨架，且不影响后续用重写版替换。
