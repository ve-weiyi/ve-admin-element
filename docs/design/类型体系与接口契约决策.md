# 类型体系与接口契约决策

> 适用范围：blog-admin（Vue 3 + Element Plus + Vite 后台前端）
> 决策日期：2026-09-11
> 关联分支：`feature/main`（基于 `release/template`）
> 关联文档：[模板功能边界与瘦身决策](模板功能边界与瘦身决策.md)

## 一、背景

以新模板为基座重建 blog-admin 时，派生分支（旧实现）与模板在**类型组织方式**、**工程化严格度**、**请求契约**三处存在方向性分歧。这三者互相牵制——它们共同决定了"接口层怎么定义、怎么校验、怎么调用"。

本文记录这三处的决策与依据。

## 二、类型体系决策

### 2.1 分歧

| | 模板 | 派生分支 |
|---|---|---|
| 全局类型 | 废弃，业务类型一律显式导入 | 保留环境声明，业务响应类型为全局 |
| 响应包装类型 | `ApiResult`（仅请求层内部使用，全仓 4 处引用） | `ApiResponse`（全仓 169 处引用，33 个文件） |
| 声明文件位置 | 仓库根的类型目录（环境、模块、路由增强等） | 源码内的类型目录（含界面设置类型） |

### 2.2 决策

**保留"业务响应类型为全局声明"的做法**，但**只保留真正的契约类型**，不整体照搬派生分支的声明文件。

保留：响应信封（`ApiResponse` / `IApiResponse`）、分页结构（`PageResult`）、下拉选项（`OptionItem`）。

不带过来，各有原因：

| 派生分支的声明 | 不带的原因 |
|---|---|
| 应用信息常量（`__APP_INFO__`） | 模板的环境声明文件已提供，且更完整（含构建时间戳） |
| 路由元信息增强（`RouteMeta`） | 模板的路由声明文件已提供 |
| 标签页视图类型（`TagView`） | 模板采用就近定义（归属标签页状态），消费方显式导入 |
| 应用设置类型（`AppSettings`） | 派生分支中已无人使用，且形状与模板的新设置模型冲突（旧为单一主题色 + 三种布局，新为主题色板 + 五色 + 标签页风格 + 双列布局） |
| 第三方组件模块声明 | 对应依赖尚未引入，引入时再补 |

### 2.3 依据

选型的主要依据是**引用规模**而非教条：派生分支侧有 169 处引用、模板侧仅 4 处，改为显式导入是纯粹的机械改动而收益（对齐上游）有限；而在两个方向都能走通的情况下，保留全局声明让搬迁期的改动集中在派生分支一侧，风险更可控。

需要明确的是：这一选择**偏离了模板"废弃全局类型"的方向**。代价是后续每次跟模板升级、遇到类型声明相关变更时，需要单独判断本文保留的这几个全局类型是否受影响。这是有意接受的代价。

## 三、工程化严格度决策

### 3.1 分歧

派生分支的类型配置**声明为严格模式，但关闭了空值检查**（以及若干细分严格规则）。这使"参数声明为可选、函数体却无条件解引用"的写法得以通过校验。

模板的类型配置是真正严格的。

### 3.2 决策

**保持模板的严格配置**，派生分支代码中暴露出的违规**就地修正**，不通过放宽配置来消除。

### 3.3 已知影响

**这是搬迁期的持续性工作，不是一次性的。** 接口层迁入即暴露 5 处违规，性质全部相同：签名声明参数可选，函数体无条件解引用。这些是真实的潜在空值缺陷，不是纯粹的写法问题。

后续搬迁的业务代码规模远大于接口层，同类违规预计还会有若干批。处理原则一致：**修正签名使其如实反映契约，而不是放宽校验**。

## 四、请求契约与环境的耦合

### 4.1 结论

接口前缀环境变量、请求实例的基地址、各接口的路径写法、开发代理的重写规则，这**四者是一组耦合约定**，必须一同变更；单独改动其中任何一项都会产生静默错误。

### 4.2 派生分支与模板的两种自洽配对

| | 模板 | 派生分支 |
|---|---|---|
| 接口前缀环境变量 | 仅作为**代理前缀**（开发态转发用） | 是**后端真实路径的一部分** |
| 请求实例基地址 | 取该前缀 | 留空 |
| 接口路径写法 | 不含前缀 | 含完整前缀 |
| 代理重写规则 | **剥离**前缀 | **恒等**（不改写） |

两者都自洽，因为它们对"该前缀是什么"的理解不同。

### 4.3 关键约束

本项目后端的接口前缀是**真实路径的一部分**（不是仅用于转发的代理前缀）。因此：

> 迁移到本项目后端的配置时，**代理重写规则必须是恒等的**，不能剥离该前缀；否则转发到后端的路径会缺少前缀段而返回不存在。

这一条修正了此前"恢复模板标准做法（剥离前缀）"的初步判断。

### 4.4 一次已发生的教训

在补齐环境配置时，只改了接口前缀变量而未同步其余三项，产生了"前端可跑（有 mock 兜底）、但对真实后端会请求到错误路径"的静默错配。

**暴露过程值得记录**：该错配不会导致编译失败或页面报错，因为开发态的 mock 用同一套拼接规则注册，两边一致故能匹配。它只在"关掉 mock、连真实后端"时显现。

**处理**：该适配与请求层实现属于同一批变更，归入基础设施适配阶段一并处理，期间保持 mock 开启以维持开发态可用。

## 五、遗留

1. **请求层的四项配对变更**尚未落地，归入基础设施适配阶段
2. **开发态 mock 开关**：待派生分支的本地路由兜底机制落地后关闭（关闭后开发态将直连后端）
3. **第三方组件的模块声明**：待引入对应依赖时补充
